# Методика испытаний: ввод трёх камер (2× Daheng + тепловизор)

> Статус: подготовлено (провести, когда приедут камеры)
> Обновлён: 2026-07-10
> Автор: Архипов Григорий

Целевая конфигурация — **2× Daheng NS-301UCL** (стереопара) + **PLUG617R** (тепловизор),
каждая камера — свой процесс `camera_service` со своими портами (ADR-0005). Код готов и частично
проверен на одиночной ME2P; здесь — план испытаний, которые нельзя провести без всех трёх камер.

Обозначения статуса: ☐ не проведено · ☑ пройдено · ✗ провалено. Заполнять при прогоне.

## 0. Предусловия

- Все три камеры подключены к Jetson по USB 3.0; права настроены
  ([drivers-setup](../04-hardware/drivers-setup.md)).
- Тепловизору нужна **aarch64** `libGuideUSBCamera.so` в корне проекта на Jetson (иначе тип
  `thermal` не собирается — см. [thermal-usb3-scsdk](../04-hardware/thermal-usb3-scsdk.md)).
  Проверка: `cmake -S . -B build` печатает «Guide SDK найден — тепловизор включён».
- Замер потоков/задержки — `tools/tune_viewer.py` с ПК по прямому Ethernet
  ([direct-ethernet](../04-hardware/../09-operations/deployment.md)); порт control/rtsp — на камеру.

## Тест-кейсы

### TC-20. Перечисление и различение камер (FR-01)
- **Предусловие:** подключены обе Daheng (одинаковый VID:PID `2ba2:4d55`).
- **Шаги:** `./build/camera_service --list-cameras`.
- **Ожидаемо:** в списке **две** Daheng с **разными** серийниками (+ модель). Тепловизор
  `04b4:f9f9` в этом списке НЕ появляется (он не Daheng) — проверяется отдельно (TC-24).
- **Критерий:** два разных SN видны и совпадают с наклейками на камерах.

### TC-21. Заполнение конфига и запуск по серийнику
- **Шаги:** вписать серийники левой/правой камеры в `config/cameras.json` (cam0/cam1);
  `./build/camera_service --config config/cameras.json --list` → проверить записи;
  запустить каждую по отдельности: `--name cam0`, затем `--name cam1`.
- **Ожидаемо:** cam0 открывает ИМЕННО левую камеру, cam1 — правую (по SN, не по индексу).
- **Критерий:** поменяв SN местами в конфиге, получаем зеркальную привязку — подтверждает выбор по SN.

### TC-22. Три потока одновременно (FR-41)
- **Шаги:** `bash scripts/run_cameras.sh start`; с ПК открыть три потока
  `rtsp://<jetson>:8554|8556|8558/cam0` в трёх вьюерах.
- **Ожидаемо:** три независимых видеопотока (2× RGB + тепло) идут параллельно.
- **Критерий:** все три декодируются без фатальных ошибок; FPS каждого стабилен ≥ целевого −10%.

### TC-23. Стереосинхронизация по временным меткам
- **Контекст:** метки захвата (`CLOCK_MONOTONIC`) обоих RGB-процессов — в одном временном
  домене (один хост), поэтому сопоставимы. SEI несёт метку каждого кадра.
- **Шаги:** снять с cam0 и cam1 метки захвата (SEI) синхронного события (например, вспышка/движение
  в поле зрения обеих); сравнить метки соседних кадров.
- **Ожидаемо:** программные метки позволяют сопоставить кадры пары; расхождение = 1/FPS + джиттер
  (камеры не имеют аппаратного триггера — синхронизация программная, см. решение по вехе).
- **Критерий:** измерить и задокументировать типичный разброс меток (мс) — вход для оценки глубины.

### TC-24. Тепловизор: изображение + радиометрия (FR-20/21)
- **Шаги:** `--name thermal`; вьюер на `:8558`; `stats` по control `:8559` → поле `temps_c`.
- **Ожидаемо:** видимое тепловое изображение (grayscale) в потоке; `temps_c.{hot,cold,cursor,mean}`
  в °C. Навести на объект известной температуры (кипяток ~100°C / лёд ~0°C).
- **Критерий:** значения `hot/cold` правдоподобны и реагируют на источник; погрешность в паспорте камеры.

### TC-25. Отказоустойчивость: отключение/переподключение камеры (vision, критично)
- **Шаги:** при работающих трёх процессах физически отключить одну камеру (USB), подождать,
  подключить обратно.
- **Ожидаемо:** (а) остальные два процесса продолжают работать без сбоя (изоляция, ADR-0005);
  (б) процесс отключённой камеры НЕ падает аварийно — сообщает об ошибке и пытается восстановиться,
  либо завершается штатно; (в) после возврата камеры поток восстанавливается (возможно, рестартом
  процесса супервизором).
- **Критерий:** нет аварийного завершения; соседние камеры не затронуты; восстановление задокументировано.
- **Заметка:** сейчас одиночный процесс при потере устройства завершится — нужен супервизор/рестарт
  (systemd `Restart=on-failure` или доработка `run_cameras.sh`). Проверить и оформить.

### TC-26. Потеря и повторное подключение клиента
- **Шаги:** во время стрима убить/перезапустить клиента (ffplay/вьюер).
- **Ожидаемо:** сервис не падает; при повторном подключении клиент получает поток (форс-IDR на PLAY).
- **Критерий:** повторный `rtsp://` успешен без перезапуска сервиса (уже подтверждено на 1 камере — TC-10).

### TC-27. Полоса USB при трёх камерах
- **Контекст:** несколько камер на одной шине упираются в полосу → неполные кадры
  ([cameras.md](../04-hardware/cameras.md)).
- **Шаги:** поднять все три; поднимать разрешение/FPS Daheng, следить за пропаданием/битыми кадрами.
- **Ожидаемо:** найти рабочие пределы; при необходимости — `DeviceLinkThroughputLimit`/децимация/FPS-cap
  (ручки уже есть в control-канале).
- **Критерий:** задокументировать максимум одновременных настроек без потери кадров; при нехватке —
  подобрать пресеты (in/out) под трёхкамерный режим.

### TC-28. Задержка каждого потока
- **Шаги:** `tools/tune_viewer.py` на каждый порт; снять glass-to-glass задержку и FPS.
- **Ожидаемо:** на NS-301UCL (0.3 Мп) задержка заметно ниже, чем на ME2P (26 Мп); тепло — по своему тракту.
- **Критерий:** зафиксировать задержку/FPS по каждой камере; сверить с целевым TBD из
  [vision](../00-overview/vision.md) (значение определяется по итогам этих замеров).

## Что проверено заранее (на одиночной ME2P, 2026-07-10)

- Перечисление Daheng и **открытие по серийнику** (`GX_OPEN_SN`) — работает.
- Конфиг-driven запуск (`--config/--name/--list`) и `run_cameras.sh` — работает; **изоляция сбоев**
  подтверждена: при плохом SN у cam1 и несобранном thermal — cam0 продолжал работать.
- Драйвер тепловизора `ThermalCamera` (C++, GuideUSBCamera) — компилируется и линкуется с aarch64 SDK,
  без камеры отказывает штатно (без краха). Рантайм — по TC-24.

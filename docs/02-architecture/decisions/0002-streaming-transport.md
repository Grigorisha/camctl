# ADR-0002: Транспорт видеопотока — RTSP/RTP + H.264 (ffmpeg)

> Статус: принято
> Дата: 2026-06-29
> Автор: Архипов Григорий
> Заменяет / заменено: —

## Контекст

Сервис должен отдавать видео с камер внешнему потребителю по сети, в том числе
клиенту коллеги. Сырые кадры (Daheng — до 2048×1536, тепловизор — 640×512) гнать без
сжатия дорого по полосе и не имеет стандартного клиента. Сами камеры RTSP/RTP не
отдают (это USB-устройства без сетевого стека) — вещание реализуется на хосте.

Дополнительная сила: `ffmpeg` **уже используется** в проекте (превью тепловизора через
`ffplay`), и коллега использует его же на стороне **клиента**. Значит, формат потока
должен без трения открываться средствами ffmpeg.

## Рассмотренные варианты

1. **Сырые кадры через сокет / shared memory** — минимальная задержка локально, но
   огромная полоса по сети, нет стандартного клиента, всё пишем сами.
2. **REST/HTTP или gRPC с кадрами (raw/JPEG)** — просто для управления и метаданных,
   но для видео тяжело по полосе и по задержке; покадровый JPEG неэффективен.
3. **RTSP/RTP + H.264** — стандарт видеостриминга: H.264 сжимает поток, доставка по
   RTP (UDP, низкая задержка), сессия по RTSP; открывается любым стандартным клиентом
   (ffmpeg/ffplay/VLC). Совпадает с инструментом коллеги.

## Решение

Видео отдаём как **H.264 поверх RTP**, сессия — по **RTSP**. Реализация — через
**ffmpeg** (на десктопе кодер `libx264`, на Jetson — аппаратный NVENC). Это **data
plane** (поток кадров). **Control plane** (configure/start/stop, метаданные) выбирается
отдельно и остаётся открытым вопросом API.

Для точки-точка и отладки допустим «чистый» RTP (`udpsink`/`udpsrc`) без RTSP.

## Обоснование

Стандарт и совместимость: поток открывается готовым клиентом коллеги на ffmpeg, без
своего протокола. H.264 резко снижает полосу против сырых кадров. RTP/UDP даёт низкую
задержку для живого видео. Решение переносится на Jetson, где H.264 кодируется
аппаратно (NVENC), не нагружая CPU.

## Последствия

- **Плюсы:** стандартный, совместимый с клиентом коллеги формат; сжатая полоса; низкая
  задержка; переносится на Jetson с аппаратным кодеком.
- **Минусы / цена:** добавляются задержка кодирования и потери от сжатия (компромисс
  качество/битрейт); зависимость от сборки кодера — pip-wheel `opencv-python-headless`
  **без GStreamer**, поэтому вещание делаем через ffmpeg/GStreamer напрямую, а не через
  `cv2.VideoWriter`; нужно управлять параметрами кодека (битрейт, GOP, профиль).
- **Дальнейшие шаги:** задача T-007 (вещание H.264 + RTSP/RTP); описать стрим-эндпоинты
  в [API](../../03-api/overview.md); зафиксировать целевые битрейт/задержку в
  [НФТ](../../01-requirements/non-functional.md) (NFR-12/13); требования FR-41, FR-42.

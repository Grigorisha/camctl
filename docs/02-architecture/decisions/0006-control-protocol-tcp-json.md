# ADR-0006: Протокол управления — TCP + JSON

> Статус: принято
> Дата: 2026-07-02
> Автор: Архипов Григорий
> Заменяет / заменено: закрывает вопрос транспорта управления из [../overview.md](../overview.md)

## Контекст

Клиент должен в реальном времени менять параметры камер (экспозиция, усиление, баланс
белого, разрешение/ROI, FPS, пиксельформат и т.д.) и, позже, внутренние параметры
сервиса. Видео идёт отдельно (RTP/UDP, [ADR-0004](0004-streaming-inhouse-nvenc.md)); тут
речь только про **control plane**. Требование: не HTTP, минимум зависимостей.

## Рассмотренные варианты

1. **REST/HTTP** — привычно, но нужен http-стек и это явно отклонено.
2. **gRPC** — эффективно, но тяжёлая зависимость (protobuf/grpc).
3. **TCP + строчный JSON, самописный** — надёжная доставка (TCP), человекочитаемо,
   минимум зависимостей, легко расширять.

## Решение

Управление — **отдельный TCP-канал, строчный JSON** (запрос→ответ + асинхронные события).
Ядро — **generic `get_params`/`set_params` поверх реестра параметров**, чтобы новые
параметры (камеры и сервиса) добавлялись без изменения протокола.

Команды: `get_capabilities`, `get_params`, `set_params`, `apply_preset`, `save_preset`,
`get_status`. События: `{"event":"status","state": ok|reconnecting|no_signal, ...}`.
Ответ: `{"ok":true,...}` / `{"ok":false,"error":...,"code":...}`. Детали — в
[../../03-api/overview.md](../../03-api/overview.md).

## Обоснование

TCP даёт гарантированную доставку команд (видео — UDP отдельно). JSON расширяем и
отлаживаем «глазами». Реестр параметров отделяет протокол от набора параметров — можно
добавлять настройки, не трогая формат. JSON парсим своим минимальным парсером.

## Последствия

- **Плюсы:** минимум зависимостей; расширяемость без слома протокола; читаемость; чёткое
  разделение control (TCP) и data (UDP).
- **Минусы / цена:** свой парсер JSON и свой цикл сервера; версионирование протокола — на нас.
- **Дальнейшие шаги:** реализовать `control/` (TCP-сервер, JSON, ParamRegistry, пресеты);
  описать команды и коды ошибок в API.
